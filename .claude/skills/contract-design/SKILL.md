# contract-design — 계약 설계

서비스에서 일어나는 사건을 시간순으로 늘어놓고 업무 흐름을 찾는 방식(이벤트 스토밍)을 씁니다. 여러 관점의 서브에이전트로 빠진 사건을 보완하고, 사건을 묶어 구역(BC)과 계약을 정합니다.

## 입력
- `docs/prd.md`: 문제, 지표, 정책, 예외 케이스
- `docs/screens.md`: 화면 흐름과 화면별 예외
- 이미 있는 `docs/decisions/`

## 1. 관점별 사건 찾기 (서브에이전트 병렬)
아래 네 관점마다 general-purpose 서브에이전트를 하나씩 띄웁니다. 각자 "~됐다" 형태의 과거형 사건을 시간순으로 뽑습니다.
| 관점 | 보는 것 |
|---|---|
| 사용자/제품 | 사용자 여정, 목표, 지표 |
| 화면·사용 흐름 | 화면 전환, 사용자 행동, 화면별 예외 |
| 운영 | 사람이 처리하는 일, 승인·취소·환불 같은 운영 예외 |
| 개발 | 상태 변경, 실패, 재시도, 중복, 동시 처리 |

## 2. 합치기
- 사건을 하나의 타임라인으로 합칩니다. 같은 사건의 다른 이름은 하나로 통일합니다 (예: "등록됨" / "생성됨" → `ItemCreated`).
- 사건마다 아래를 붙입니다.
  - **명령:** 누가 무엇을 해서 일어나는가
  - **정책:** 이 사건 다음에 자동으로 일어나는 일
  - **읽기 모델:** 결정에 필요한 정보
- 사건이 아닌 것(필터, 정렬, 화면 토글)과 명령 거절(입력 오류, 갈 수 없는 상태 변경)은 따로 적습니다.

## 3. 경계 나누기
- 상태와 규칙을 함께 책임지는 사건끼리 묶어 구역(BC)을 정합니다.
- 구역 사이를 오가는 사건은 이벤트 계약 후보이고, 구역 사이의 조회는 Port 후보입니다.
- 확신이 없는 경계는 판단과 근거를 `docs/design/`에 적어 둡니다. 구현하면서 다시 봅니다.
- 정할 수 없는 질문은 한 번에 모아 Orchestrator(또는 사용자)에게 선택지와 추천안으로 묻습니다.

## 4. 산출물 (사용자 승인 전에는 초안)
- `docs/glossary.md`: 용어, 영문 표기, 정의, 쓰지 않는 말
- `docs/design/contract-design.md`: 타임라인, 대안, 논의 (사람이 읽는 기록)
- `docs/decisions/0001-<제목>.md`: 확정한 구역과 책임, 구역 사이 연결, 정책 (`docs/decisions/0000-template.md` 형식)
- 계약 코드 파일(`.claude/project.conf`의 `CONTRACT_PATTERNS`, 기본값: `src/modules/shared/events/*`, `src/modules/*/ports/*`): 타입만 작성. 코드 뼈대가 아직 없으면 다음 작업으로 넘깁니다.

## 5. 검증과 승인 (최대 2차)
- 문서 PR도 `/verify`로 Checker에게 맡깁니다. 판정 기준은 코드와 같습니다: **확정된 높음 0건이면 PASS, 최대 2차**.
- 계약 문서의 높음: 용어 하나에 정의가 둘, 같은 사건에 이름이 둘, PRD 정책과 반대되는 결정, 어느 구역도 맡지 않는 상태, 구역끼리 서로의 상태를 직접 바꾸는 연결.
- 낮음(표현, 예시 부족, 나중에 정해도 되는 값)은 "후속 과제"로 보냅니다. **완벽해질 때까지 돌리지 않습니다.** 2차도 FAIL이면 사용자에게 올립니다.
- 사용자 승인을 받아 머지한 뒤 `main`의 머지 커밋에 `contract-v1` 태그를 붙입니다.
