# event-storming — 도메인 설계

사례 글의 방식을 따릅니다. 서비스에서 일어나는 사건을 시간순으로 늘어놓고 업무 흐름을 찾습니다. 여러 관점의 서브에이전트로 빠진 사건을 보완합니다.

## 입력
- `docs/prd.md`와 Notion PRD
- `docs/screens.md`와 Figma 화면
- PLAN 3절 (용어 초안, BC 초안, 정책 목록)

## 1. 관점별 사건 찾기 (서브에이전트 병렬)
아래 네 관점마다 general-purpose 서브에이전트를 하나씩 띄웁니다. 각자 "~됐다" 형태의 과거형 사건을 시간순으로 뽑습니다.
- **PM:** 고객 여정과 지표
- **디자이너:** 화면 전환과 사용자 행동
- **상담원(운영):** 상담, 개통, 지급 처리와 예외
- **개발자:** 상태 변경, 실패, 재시도, 중복

## 2. 합치기
- 사건을 하나의 타임라인으로 합칩니다. 같은 사건의 다른 이름은 하나로 통일합니다 (예: "신청됨" / "접수됨" → `ApplicationSubmitted`).
- 사건마다 아래를 붙입니다.
  - **명령:** 누가 무엇을 해서 일어나는가
  - **정책:** 이 사건 다음에 자동으로 일어나는 일
  - **읽기 모델:** 결정에 필요한 정보

## 3. 경계 나누기
- 상태와 규칙을 함께 책임지는 사건끼리 묶어 BC를 정합니다.
- BC 사이를 오가는 사건은 이벤트 계약 후보이고, BC 사이의 조회는 Port 후보입니다.
- 확신이 없는 경계는 판단과 근거를 `docs/design/`에 적어 둡니다. 구현하면서 다시 봅니다.

## 4. 산출물 (사용자 승인 전에는 초안)
- `docs/glossary.md`: 용어, 정의, 영문 표기, 쓰지 않는 말
- `docs/design/event-storming.md`: 타임라인, 대안, 논의
- `docs/decisions/0001-bounded-contexts.md`: 확정한 BC와 책임
- `src/modules/shared/events/` 와 `src/modules/*/ports/`: 타입만 작성 (Phase D3)

사용자 승인을 받은 뒤 `contract-v1` 태그를 붙입니다.
