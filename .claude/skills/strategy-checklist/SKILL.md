# strategy-checklist — 설계

목표는 구현 전에 **무엇을 만들고, 어떤 상태를 완료로 볼지** 정하는 것입니다. 이 스킬은 코드를 쓰지 않습니다.

## 1. 자료 먼저 읽기 (질문하기 전에)
- `docs/board.md`에서 작업 ID, 완료 기준, 담당 구역을 확인합니다.
- `docs/glossary.md`, `docs/decisions/`, `docs/prd.md`의 정책과 예외 케이스를 읽습니다.
- 담당 구역의 현재 코드와 다른 구역의 `ports/`, `shared/events/`(계약 파일)를 읽습니다.
- 이미 답이 있는 내용은 묻지 않습니다.

## 2. 질문하기 (grill me)
자료로 답할 수 없는 것만, **한 번에 하나씩** 묻습니다. 질문마다 선택지와 추천안을 함께 제시하고, 결정은 사람이 내립니다.
- **목적:** 이 작업이 PRD의 어떤 가설이나 지표와 연결되는가?
- **제약:** 지켜야 할 정책, 숫자·날짜 경계, 상태 전이
- **예외:** 중복, 취소, 동시 처리, 빈 값, 경계값 바로 바깥
- **성공 기준:** 어떤 입력에 어떤 결과가 나와야 완료인가?
- **계약:** 지금 있는 이벤트와 Port로 충분한가? 부족하면 구현하지 않고 `/contract-change`로 요청합니다.

## 3. 체크리스트 작성
`docs/checklists/<작업ID>.md`에 `docs/checklists/_template.md` 형식으로 저장합니다. 이 파일만 보고 새 세션에서 구현할 수 있어야 합니다.

```markdown
# T-xx <작업 이름>
- 담당 구역 / 수정 가능 경로:
- 계약 버전: contract-vN

## 합의한 요구사항
## 결정과 근거        (질문에 대한 답과 그 이유)
## 테스트 케이스       (입력 → 기대 결과. 정책·경계값·예외 포함)
## 범위 밖            (이번에 하지 않는 것)
## 완료 기준          (board의 완료 기준 + 테스트 실행 건수 기준)
```

## 4. 멈추기
체크리스트를 저장하면 **여기서 멈춥니다.** 구현으로 넘어가지 않습니다.
- Orchestrator(또는 사용자)에게 체크리스트 경로를 알리고 확인을 기다립니다.
  ```bash
  herdr agent prompt orchestrator "<작업ID> 체크리스트 완성: docs/checklists/<작업ID>.md"
  ```
  herdr를 쓸 수 없으면 SendMessage로 보냅니다.
- 확인을 받으면 구현은 **새 세션**(`/clear` 뒤)에서 `tdd-helper`로 시작합니다. 맥락이 길어지면 판단이 흐려지기 때문입니다.
