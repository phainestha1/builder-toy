# domain-review — 리뷰와 검증

> 내장 `/code-review` 명령과 이름이 겹치지 않도록 `domain-review`라는 이름을 씁니다. 이 프로젝트의 계약, 정책, 구역 규칙을 기준으로 리뷰합니다.

## 입력
브랜치 이름, 작업 ID, 완료 기준, 차수(1차 / 2차)만 받습니다. Builder의 설명, 의도, 자체 평가는 근거로 쓰지 않습니다.

## 판정 기준
- **PASS:** 완료 기준을 모두 충족하고, 확정된 **높음** 지적이 0건이면 PASS입니다. 낮음 지적이 남아도 PASS입니다.
- **높음:** 테스트 실패·0건, 계약(이벤트·Port·용어) 위반, 구역 경계 위반, 정책을 반대로 구현한 것, 보안·개인정보 문제(인증 우회, 권한 우회, 시크릿 노출, 인젝션). 그 밖은 낮음입니다.
- **낮음은 최대 5건**만 보고합니다. 영향이 큰 순서로 고릅니다. Orchestrator가 보드의 "후속 과제"로 옮깁니다.
- **최대 2차:** 2차도 FAIL이면 Orchestrator가 사용자에게 올립니다. 완벽해질 때까지 돌리지 않습니다.

## 1. 기준 모으기
- `docs/checklists/<작업ID>.md`: 합의한 요구사항과 테스트 케이스
- `docs/glossary.md`, `docs/decisions/`, `.claude/rules/`

## 2. 직접 실행
- `git diff origin/main...HEAD`로 변경 범위를 확인합니다. (2차면 `git diff <1차 커밋>..HEAD`만 봅니다)
- 검사 명령(`CHECK_CMD`, `.claude/project.conf`)을 실행하고 `테스트 실행 N / 통과 N`을 기록합니다. 0건이면 그 자리에서 FAIL입니다.

## 3. 테스트 관점 (Checker가 직접)
- 건너뛰기·단독 실행 표시(예: `.skip`, `.only`, `@skip`)가 커밋에 남았는가?
- 체크리스트의 테스트 케이스가 모두 테스트로 있는가? 정책마다 테스트가 하나 이상 있는가?
- 경계가 있는 규칙(날짜, 숫자 상한, 상태 전이)에서 경계 안쪽과 바깥쪽이 둘 다 테스트되는가?
- 기대값을 구현에서 베끼지 않고, 정책에서 직접 계산했는가?

## 4. 서브에이전트 (0~1개로 시작)
기본은 **없음**입니다. 아래에 해당할 때만 붙입니다.
| 조건 | 서브에이전트 |
|---|---|
| 변경이 큼 (구역 여러 개, 새 모듈, 의존 방향이 바뀜) | `arch-reviewer` |
| 인증, 권한, 개인정보, 외부 입력(폼, API, 파일, 웹훅)을 건드림 | `security-reviewer` |

둘 다 해당하면 둘 다 붙입니다. 2차 검증에서는 서브에이전트 없이 직접 확인합니다.

## 5. 지적 검증
- 높음 지적은 하나씩 `finding-verifier`에게 넘깁니다.
- **넘기는 것:** 지적 내용과 파일:줄
- **넘기지 않는 것:** 심각도, 확신도, 수정안
- 판정이 "반박"이면 지적에서 빼고 오탐 수에 셉니다. "불확실"이면 불확실로 표시해서 남깁니다 (불확실은 FAIL 사유가 아님).

## 6. 판정과 보고
- **PASS:** 완료 기준을 모두 충족했고, 확정된 높음 지적이 없음
- **FAIL:** 그 외

결과를 아래 형식으로 Orchestrator에게 보냅니다.
```
작업: T-xx · 브랜치: feat/... · 커밋: <hash> · 차수: 1차 | 2차
판정: PASS | FAIL
테스트: 실행 N / 통과 N
완료 기준: [충족] ... / [미충족] ...
지적 (높음):
- [확정] path:line — 내용
- [불확실] path:line — 내용 (근거가 부족한 이유)
지적 (낮음, 최대 5건 → 후속 과제):
- path:line — 내용
서브에이전트: 없음 | arch-reviewer | security-reviewer
오탐: N건 (finding-verifier가 반박한 높음 지적)
```
