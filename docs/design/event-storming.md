## 3. 상태 머신
**접수 (`application`)**
```
[접수] ──상담 시작──> [상담중] ──개통──> [개통완료] (끝)
   │                     │
   └──취소──> [취소] <──취소──┘
              (끝)
재접수 합침: 상태는 그대로, 재접수 횟수 +1
```

**지원금 (`reward`)** — 접수 상태와 따로 둡니다.
```
LineActivated ─┬─ 근거 있음 ──> [산정됨] ──지급 처리──> [지급완료] (끝)
               └─ 근거 없음 ──> [산정 대상 아님] (끝, 지급 불가)
개통 전 취소: 지원금 자체가 없음
```
따로 두는 이유: 지원금은 개통 뒤에야 생기고, 합치면 "개통완료는 끝 상태"(화면 05)와 "그 뒤 지급완료"가 부딪힙니다. 어드민 메뉴도 "접수 관리"와 "지원금 지급"으로 나뉘어 있습니다.

## 4. 경계 논의와 대안

### 4.1 `consultation` BC — 안 A 채택
- **문제:** PLAN 초안은 접수 상태를 `application`, 상담·개통을 `consultation`에 나눴습니다. 그런데 화면의 상태 머신은 `접수 → 상담중 → 개통완료/취소` 하나입니다. 두 BC가 한 상태 머신의 일부씩을 가지면, 이벤트가 엇갈릴 때 상태가 어긋납니다. "취소" 명령의 주인도 모호해집니다.
- **안 A (채택):** v1에서 `consultation`을 `application`에 합칩니다. 접수 상태 머신 전체를 `application`이 갖습니다.
- **안 B (버림):** `consultation`이 상태 머신 전체를 갖고, `application`은 접수 생성과 재접수 합치기만 맡습니다. 상담 배정이 생기면 옮기기 쉽다는 장점이 있습니다.
- **B를 버린 이유:** v1에는 상담 배정·상담 결과·설치 일정이 없어 `consultation`이 따로 가질 상태가 없습니다. 상태 머신이 두 BC로 쪼개지는 위험만 남습니다.
- **다시 볼 때:** 상담 배정이나 상담 결과 기록이 범위에 들어오면 다시 나눕니다 (ADR 0001 결과).

### 4.2 지원금 공식의 위치 — `catalog`
- **문제:** 계산기(03), 요금제 비교(02), 지원금 산정(개통 뒤)이 같은 공식을 써야 합니다. PRD 운영 원칙이 "계산 금액과 실제 지급액이 달라지지 않게"입니다.
- **채택:** 기준표와 공식을 `catalog`에 두고 `CatalogPort`로 공개합니다. `reward`는 산정 결과와 지급 상태만 갖습니다.
- **버린 안:** 기준표와 공식을 `reward`로 옮기는 안. 그러면 고객 화면의 비교·계산이 지급 BC에 기대게 됩니다. 공식을 `shared`에 두는 안은 "shared에 BC 로직을 두지 않는다" 규칙 위반입니다.

### 4.3 기준표가 바뀌는 경우
- 계산한 뒤 개통 전에 기준표가 바뀌면 "계산 금액 = 지급 금액" 원칙이 깨질 수 있습니다.
- 그래서 기준표를 버전 단위로 만들고 고치지 않습니다. 접수할 때 기준표 버전을 스냅샷하고, 개통 때 그 버전으로 다시 계산합니다 [가정].

### 4.4 전화번호 열람 기록 — `application`
전화번호를 가진 BC가 열람 기록도 갖습니다. 다른 BC가 쓰지 않으므로 이벤트 계약이 필요 없습니다.

### 4.5 변형을 접수에 남기는 방법
어드민 목록에 "변형" 열이 있습니다. 접수할 때 `application`이 `ExperimentPort`로 방문자의 변형을 읽어 접수에 남깁니다. 전환은 `experiment`가 `ApplicationSubmitted`의 `visitorId`로 자기 배정을 찾아 기록합니다.

## 7. 신뢰성 메모 (구현 때 다시 봄)
개발자 관점에서 나온 내용입니다. 정책 R4, R5, A5의 구현 방법 후보이고, 확정은 T-D2·T-E1 이후 구현 작업에서 합니다.
- **멱등성:** 이벤트마다 `eventId`를 두고, 받는 BC가 처리한 `eventId`를 상태 변경과 같은 트랜잭션에 기록합니다.
- **재접수 동시성:** SQLite에서 "7일 안 접수 조회 → 합치기 또는 새로 만들기"를 쓰기 트랜잭션(`BEGIN IMMEDIATE`) 하나로 처리합니다.
- **중복 지급:** 지원금에 접수 ID 유일 제약을 걸고, 지급은 `산정됨`일 때만 바뀌게 조건부로 갱신합니다.
- **이벤트 유실:** `LineActivated`가 `reward`에 닿지 않으면 지원금이 생기지 않습니다. 동기 인메모리 버스로 충분한지, 아웃박스(이벤트를 DB에 먼저 쓰고 나중에 보내는 방식)까지 만들지는 T-E1에서 정합니다.

## 8. 지표 메모
- **지표 1 (변형별 접수 전환율):** 분모는 집계 제외가 아닌 노출 방문자, 분자는 그중 전환한 방문자입니다. 배정 실패 방문자를 넣으면 A안이 부풀려집니다.
- **지표 2 (계산기 사용자의 접수 전환율):** 분모는 계산기 사용자, 분자는 그중 전환한 방문자입니다. 계산기 사용자는 원래 의지가 강할 수 있어, 인과가 아니라 상관으로 읽습니다.
- 재접수 합침을 전환으로 세지 않으므로 접수 건수와 전환 수는 다른 숫자입니다.
- 실험 이벤트에는 전화번호를 넣지 않고 접수 ID와 `visitorId`로만 잇습니다.
- 노출 뒤 며칠 안의 접수까지 전환으로 볼지(전환 기간)는 M7 실험 설계에서 정합니다.
