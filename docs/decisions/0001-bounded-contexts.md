## 결정

### 1. BC
| BC | 책임 | 갖는 상태 |
|---|---|---|
| `catalog` | 요금제, 지원금 기준표(버전 관리), 지원금 계산 공식 | 요금제, 기준표 버전 |
| `application` | 접수 생성, 재접수 합치기, 접수 상태 머신, 전화번호 열람 기록 | 접수, 계산 결과 스냅샷, 상태 변경 기록, 열람 기록 |
| `reward` | 개통 뒤 지원금 산정, 지급 기록 | 지원금(산정 결과, 지원금 상태) |
| `experiment` | 변형 배정, 노출·계산·전환 기록, 집계 제외 | 배정, 노출, 계산 기록, 전환 |
| `shared` | 이벤트 버스, DB 연결, 어드민 인증, 시계 같은 기술 인프라만. 상담원 계정과 `counselorId`의 주인은 어드민 인증이다. `counselorId`는 라우트가 세션에서 꺼내 유스케이스 인자로 넘긴다 | 상담원 계정(인증용) |

### 2. BC 사이 연결
**이벤트 (계약 후보, 타입은 T-D2)**
| 이벤트 | 발행 | 받는 BC와 동작 |
|---|---|---|
| `ApplicationSubmitted` | `application` | `experiment`: 접수의 배정 변형을 기준으로 전환을 기록 (화면이 직접 기록하지 않음) |
| `ApplicationMerged` | `application` | 없음 |
| `ConsultationStarted` | `application` | 없음 |
| `LineActivated` | `application` | `reward`: 지원금 산정 |
| `ApplicationCancelled` | `application` | 없음 |
| `RewardCalculated` | `reward` | 없음 |
| `RewardPaid` | `reward` | 없음 |

**Port (조회 전용, 타입은 T-D2)**
| Port | 제공 BC | 쓰는 쪽 | 용도 |
|---|---|---|---|
| `CatalogPort` | `catalog` | `application`, `reward` | 현재 기준표 버전으로 지원금 계산(접수 때 스냅샷), 지정한 기준표 버전으로 지원금 계산(개통 때 산정) |
| `ApplicationPort` | `application` | `reward` | 접수의 계산 결과 스냅샷(산정 근거) 조회 |
| `ExperimentPort` | `experiment` | `application` | 방문자의 배정 변형 조회 (접수에 변형을 남김) |

Port는 BC 사이 조회에만 쓴다. 화면(`src/app`)은 각 BC의 `application` 유스케이스만 호출한다. 계산기·요금제 비교는 `catalog`의 조회 유스케이스를, 어드민의 지원금 표시는 `reward`의 조회 유스케이스를 쓴다.
- 계산 기록: 라우트가 `catalog`의 계산 유스케이스를 부른 뒤 `experiment`의 기록 유스케이스를 부른다. 계산이 거절되면(범위 밖 입력, 기준표에 없는 요금제) 기록하지 않는다.
- 04 요약 카드: 접수 화면에 들어올 때 `catalog`의 계산 유스케이스로 현재 버전 금액을 계산해 보여 준다.
- 어드민 목록: 라우트가 `application` 조회와 `reward` 조회 결과를 접수 ID로 붙인다.

### 3. 정책 (테스트로 옮길 규칙)
[가정] 표시는 데이터 없이 정한 값이다.

**experiment**
- E1. 한 방문자는 한 실험에서 항상 같은 변형을 받는다. 방문자는 익명 쿠키의 `visitorId`로 구분한다 [가정]. 배정은 랜딩에서만 일어난다. 랜딩을 거치지 않고 02·03·04로 바로 온 방문자는 `제외`다 (실험 대상이 랜딩 소구점이라 의도한 것).
- E2. 배정에 실패한 방문자는 그 실험에서 영구히 `제외`이고 계속 A안을 본다. 다시 배정하지 않는다. `제외`는 방문자 단위다. `제외` 방문자의 노출·계산·전환도 기록하되 `제외` 표시를 달고, 지표 1·2의 분모와 분자에 넣지 않는다.
- E3. 노출은 랜딩이 보인 것(배정 변형 또는 `제외`)이고, 방문자·실험당 첫 1회만 센다 [가정].
- E4. 03 지원금 계산기에서 계산을 실행하면 `RewardEstimated`를 기록한다 (기록 경로는 2절). 계산이 거절되면 기록하지 않는다. 계산기 사용자는 이 기록이 있는 방문자로 한정한다. 02 요금제 비교의 카드 금액을 본 것은 넣지 않는다 (지표 2 "계산기 사용자의 접수 전환율").
- E5. 전환은 `experiment`가 `ApplicationSubmitted`를 받아 방문자·실험당 1회만 기록한다. 판정 기준은 접수에 기록된 배정 변형 하나이고, `experiment`의 현재 배정은 보지 않는다. 배정 변형이 `제외`인 접수는 `제외` 표시를 단다. v1의 실험은 하나뿐이다 [가정]. `ApplicationMerged`는 전환이 아니다. 같은 사람이 다른 기기에서 새 접수를 만들면(예: 기존 접수가 끝 상태이거나 168시간이 지남) 다른 `visitorId`로 두 번 셀 수 있다. 알려진 한계로 둔다 [가정].

**catalog**
- C1. 지원금 계산 = 기본 지원금 + 위약금 보전액. 위약금 보전액 = `min(위약금, 보전 한도)`.
- C2. 보전 한도는 기준표 버전에 속하고 버전마다 하나다 (요금제별 값이 아님). 30만 원이다 [가정].
- C3. 약정이 없으면 위약금 보전액은 0원이다.
- C4. 남은 약정 개월은 0~36 사이 정수 개월 [가정], 위약금은 0원 이상 1,000만 원 이하 정수 원 [가정]만 받는다. 범위 밖이거나 계산 입력이 일부만 있으면 계산과 접수를 모두 거절한다 (명령 거절).
- C5. 고객이 위약금을 모르면 평균 위약금을 쓴다. 평균 위약금은 기준표 버전에 속하고 버전마다 하나다 (요금제별 값이 아님) [가정].
- C6. 기준표에 없는 요금제는 금액을 계산하지 않는다 ("지원금 상담 시 안내").
- C7. 기준표는 버전 단위로 만들고, 만든 버전은 고치지 않는다. 계산기, 요금제 비교, 접수 때 스냅샷, 지원금 산정은 모두 `catalog`의 같은 지원금 계산 공식을 쓴다.
- C8. 02 요금제 비교의 카드 금액은 약정 없음(보전액 0원) 기준의 예상 지원금, 곧 기본 지원금이다. 계산기에서 약정 없음을 고르면 같은 숫자가 나와야 한다.

**application**
- A1. 이름, 전화번호, 개인정보 동의는 필수이고, 설치 희망 지역과 상담 희망 시간대는 선택이다 [가정]. 필수 항목이 없거나 전화번호 형식이 틀리면 명령을 거절한다. 동의한 사실과 시각을 접수에 남긴다. 전화번호는 숫자만 남겨 정규화한 뒤 저장·비교하고, 01로 시작하는 10~11자리만 받는다 [가정]. `010-1234-5678`과 `01012345678`은 같은 번호다.
- A2. 고객 입력(요금제, 약정 여부, 남은 약정 개월, 위약금)이 있으면 접수할 때 서버가 그 시점의 현재 기준표 버전 [가정]으로 `CatalogPort` 계산을 다시 하고, 그 결과를 계산 결과 스냅샷(입력, 기준표 버전, 예상 지원금)으로 남긴다. 입력 검증은 C4를 따른다. 클라이언트가 보낸 버전·금액은 믿지 않는다. 04 요약 카드에 보였던 금액과 다르면 접수할 때의 값을 저장하고 완료 화면에 그 값을 보여 준다. 별도 알림이나 재확인은 하지 않는다 [가정]. 요금제가 기준표에 없으면 스냅샷이 없다. 계산 없이도 접수할 수 있다.
- A3. 같은 전화번호의 기존 접수가 마지막 접수 시각(합침 포함)부터 168시간 미만이고, 그 접수가 `접수`·`상담중`이면 새 접수를 만들지 않고 합친다 [가정]. 168시간 정각부터, 또는 기존 접수가 `개통완료`·`취소`면 새 접수를 만든다. 시각은 서버 시각(UTC)으로 비교한다. 합칠 때마다 168시간 창이 다시 시작되는 것은 의도다 [가정].
- A4. 합칠 때 규칙 [가정]:
  - 연락처성 정보(이름, 설치 희망 지역, 상담 희망 시간대, 동의 시각)는 새 값으로 바꾼다. 선택 항목이 비어 있으면 기존 값을 유지한다.
  - 계산 결과 스냅샷은 기존 접수가 `접수`일 때만 바꿀 수 있다. 새 접수에 요금제 입력이 없으면 기존 스냅샷을 유지하고, 있으면 그 입력으로 다시 계산한다. 입력한 요금제가 기준표에 없으면 스냅샷을 없앤다 (개통 뒤 `산정 대상 아님`).
  - 기존 접수가 `상담중`이면 지급 근거 스냅샷(요금제, 위약금, 기준표 버전)은 바꾸지 않는다.
  - `visitorId`와 배정 변형은 처음 접수의 값을 유지한다. 상태는 그대로 두고 재접수 횟수를 1 올린다.
  - 응답에는 "이미 접수된 상담이 있어요" 안내만 담고, 기존 접수의 내용(이름, 요금제, 금액)은 담지 않는다.
- A5. 같은 번호의 동시 접수는 하나만 새로 만들어지고 나머지는 합쳐져야 한다.
- A6. 상태 전이는 `접수 → 상담중 → 개통완료`, `접수 → 취소`, `상담중 → 취소`만 허용한다 [가정]. `개통완료`와 `취소`는 끝 상태다. `접수 → 개통완료`(상담중 건너뛰기)와 거꾸로 가는 전이는 거절한다. 지금과 같은 상태로 가는 요청은 오류 없이 무시하고 이벤트를 내지 않는다 [가정].
- A7. 상태 변경에는 처리한 상담원의 `counselorId`와 시각을 남긴다.
- A8. 어드민 목록·상세 응답에는 가린 전화번호만 담는다. 원래 번호는 열람 명령으로만 주고, 그때 누가, 언제 봤는지(`PhoneNumberRevealed`) 남긴다. 전화번호 검색은 뒷자리 4자리로만 한다 [가정].
- A9. 접수는 `visitorId`와 배정 변형을 사실로 남긴다. 배정 변형은 접수할 때 `ExperimentPort`로 읽은 값이고, 그때 배정이 없으면 `제외`다. 어드민 목록의 변형은 이 값이다.

**reward**
- R1. 지원금은 `LineActivated`를 받은 뒤에만 만든다. 개통 전에 취소한 접수에는 지원금이 없다.
- R2. 산정은 `ApplicationPort`로 계산 결과 스냅샷을 읽고, 스냅샷의 입력과 기준표 버전으로 `CatalogPort` 계산을 다시 해 금액을 정한다. 개통 요금제는 스냅샷의 요금제와 같다 (개통 때 요금제 변경은 v1 범위 밖). 상담원은 금액을 고칠 수 없고 (6절 위험), 개통 뒤 유지 기간 같은 지급 조건은 없다 [가정].
- R3. 접수에 계산 결과 스냅샷이 없으면(계산 없이 접수, 기준표에 없는 요금제) `RewardCalculated`를 내지 않고 지원금 상태를 `산정 대상 아님`으로 둔다 [가정]. 판단 근거(스냅샷 유무)는 접수 때 정해진다. 고객이 본 적 없는 금액을 만들지 않는다.
- R4. 지원금은 접수 1건에 하나만 만든다. 같은 `LineActivated`를 두 번 받아도 한 번만 산정한다.
- R5. 지급은 `산정됨`에서만 할 수 있고 한 번만 된다. 두 번째 지급 요청과 `산정 대상 아님`의 지급 요청은 거절한다. 실제 송금 없이 `지급완료`만 기록한다.
- R6. 지급 처리에는 처리한 상담원의 `counselorId`와 시각을 남긴다.

**모든 BC**
- P1. 이벤트 payload에 전화번호·이름 같은 개인정보를 넣지 않는다. 접수 ID와 `visitorId`로 잇는다.

### 4. PLAN 3절과 달라진 점
| PLAN 3절 | 이 결정 | 이유 |
|---|---|---|
| `consultation` BC (상담 배정, 상담 결과, 개통 처리) | v1에서는 `application`에 합친다 | 이번 범위에 상담 배정·상담 결과가 없어 따로 가질 상태가 없다. 나누면 하나인 접수 상태 머신이 두 BC로 쪼개진다 |
| `RewardScheduled` | `RewardCalculated` | 지급 조건 단계가 없어 "예약"이 아니다 |
| `ConsultationCompleted` | 없앤다 | 상담의 결과는 개통이나 취소다. 화면에도 대응하는 상태가 없다 |
| `catalog`: 요금제 조회, 지원금 기준표 | 지원금 계산 공식도 `catalog`가 갖는다 | 계산기 금액과 지급 금액이 같은 코드에서 나와야 어긋나지 않는다 |
| `reward`: 지원금 산정, 지급 조건 확인, 지급 | 산정 결과와 지급 상태만 갖는다. 지급 조건은 없다 [가정] | 공식은 `catalog`에 있다. PRD에 지급 조건이 정해져 있지 않다 |
| `experiment`: 노출·전환 기록 | 계산 기록과 집계 제외도 갖는다 | 핵심 지표 2와 화면 01 예외(배정 실패) 때문 |

### 5. 범위 밖
- 개통 뒤 해지, 지원금 환수: 이번 범위에 실제 송금과 통신사 연동이 없어 다룰 사실이 없다.
- 상태 되돌리기(정정): 끝 상태를 되돌리면 이미 만든 지원금과 충돌한다. 거꾸로 가는 전이를 막는 데서 멈춘다.
- 상담 배정, 상담 결과 기록, 설치 일정: 스코프에서 어드민 상태 변경으로 대신한다.
- 개통 때 요금제 변경: 개통 요금제는 접수 스냅샷의 요금제와 같다고 본다.
- 개인정보 보관 기간과 파기: v1에서는 다루지 않는다. 실서비스에서는 필요하다.

### 6. 받아들이는 위험과 알려진 한계
- 남의 번호 접수: 본인인증이 범위 밖이라, 남의 전화번호로 접수하면 진행 중인 접수를 덮어쓸 수 있다. 연습 범위라서 받아들인다. 실서비스에는 본인인증이 필요하다.
- 다른 기기 이중 집계: 같은 사람이 다른 기기에서 새 접수를 만들면 전환이 두 번 셀 수 있다 (E5) [가정].
- 같은 번호 지원금 2회: 끝 상태 뒤나 168시간 뒤의 새 접수가 다시 개통되면 같은 번호로 지원금이 두 번 생길 수 있다. 이사 후 재개통처럼 정당한 경우가 있고, v1은 번호별 지급 이력 조회가 범위 밖이라 막지 않는다.
- 고객 입력 위약금: 고객이 직접 입력한 위약금이 그대로 지급액 근거가 되고, 상담원은 고칠 수 없다. 상한(C4)으로 크기만 제한한다.

## 결과
- T-D2는 위 이벤트 7개와 Port 3개의 타입만 쓴다. payload에는 ID와 그 시점의 사실만 담고 개인정보는 넣지 않는다 (P1).
- `.claude/rules/architecture.md`의 BC 표에는 아직 `consultation`이 있다. Orchestrator가 이 결정에 맞춰 고친다.
- `.claude/rules/architecture.md`의 `shared` 설명에 "상담원 계정과 `counselorId`의 주인은 어드민 인증, 라우트가 세션에서 꺼내 유스케이스 인자로 넘긴다"를 반영한다 (Orchestrator).
- `.claude/rules/frontend.md`를 "전환은 `experiment`가 `ApplicationSubmitted`를 받아 기록하고 화면이 직접 기록하지 않는다"에 맞춰 고친다 (Orchestrator).
